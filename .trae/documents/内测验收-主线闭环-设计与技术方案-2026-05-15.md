# 内测验收（主线闭环）全视角梳理：设计方案 + 技术方案 + 跟踪与测试计划

## Summary

本计划面向「仅微信小程序（WEAPP）内测」的**全量主线闭环**：订单（发单-支付-派单-生成-发布-反馈-验收-结算）+ 个人中心（通知/收益/推广）+ 分身（创建/托管/接单执行主体）+ 社交/聊天（消息入口与上下文一致性）。目标是形成一套可执行的**验收方向**、一套可落地的**修复清单与技术改造方案**、以及可持续迭代的**缺陷跟踪 + 测试回归体系**。

放行标准：**严格放行**（P0=0，P1=0，P2可延期但不得误导用户或破坏核心闭环）。\
跟踪方式：在 GitHub 上**新建内测 Project 看板**，所有验收项拆分为 issues 并关联，支持状态流转与回归标记。

## Goals & Success Criteria（内测验收方向）

### 核心目标

1. **闭环可完成**：发单者与接单者都能完成一单的端到端闭环，且所有关键异常都有兜底路径。
2. **状态可信**：同一订单在列表/详情/匹配/处理/验收页的状态与下一步动作一致。
3. **数据可信**：金额、支付状态、结算收益一致且可解释（至少“为什么是这个数/何时到账/失败怎么处理”）。
4. **可跟踪可回归**：每个验收点都有对应 issue、复现步骤、验收标准、回归记录；每次修复后可快速跑一遍 smoke pack。

### 内测放行口径

- P0=0、P1=0
- P2：允许存在，但必须满足
  - 不误导用户（如示例数据需明确标注）
  - 不破坏核心闭环（不会导致卡死/无法继续）
  - 不引入严重风控风险（重复结算、越权接单等）

## User Task Flows（用户任务链路：验收主线）

### A. 发单者主线（订单闭环）

1. 创建订单（可选 AI 帮写）→ 价格确认
2. 支付（成功/取消/失败/回调延迟）
3. 智能匹配 → 一键派单（或手动调整策略）
4. 查看生成进度 → 进入验收准备
5. 接收发布反馈（截图/链接/验证状态）
6. 验收：通过/驳回（循环）→ 全部完成 → 结算完成

### B. 接单者主线（分身执行闭环）

1. 待接订单/订单广场 → 选择分身接单
2. 内容生成（排队/生成/预览/失败重试）
3. 发布引导（平台步骤 + 账号绑定 + 复制/保存）
4. 发布反馈（截图/链接）→ 验证（通过/失败兜底）
5. 等待验收（可催促）→ 完成收益入账 → 可提现

### C. 支撑主线（通知/收益/推广）

1. 通知：派单/驳回/支付/超时等关键事件进入站内通知并可回跳定位
2. 收益：概览/明细/提现（门槛、失败原因、重试路径）
3. 推广：邀请码生成/分享落地/统计与记录

## Proposed Changes（设计方案 + 技术方案）

以下以“内测标准”驱动，按 P0/P1/P2 输出**可落地修复包**，并明确涉及文件与验证方式。执行阶段将严格遵循“手术式修改、1–3 文件/次”的变更治理。

### Phase 0：建立“验收与跟踪”基础设施（先立规矩）

**Deliverables**

- 新建 GitHub Project：`内测验收-主线闭环`（看板列建议：Backlog / Ready / In Progress / In Review / Verify / Done）
- Issue 模板（P0/P1/P2 + 复现步骤 + 期望/实际 + 日志点 + 验收标准）
- 文档化的 Smoke Pack（20–30 分钟跑完的必通用例）

**Implementation**

- 使用 `gh` 创建 Project、批量创建 issues、打标签并加入看板（执行阶段落地）
- 在仓库新增文档（执行阶段创建）：
  - `docs/internal-test/smoke-pack.md`
  - `docs/internal-test/acceptance-checklist.md`
  - `docs/internal-test/bug-template.md`

**Verification**

- 每个 Smoke 用例能在 WEAPP 环境稳定复现并记录结果
- 每个缺陷都能在 Project 中追踪状态与回归版本

### Phase 1：P0 关闭（阻断闭环/高频崩溃/资金与风控）

#### P0-1 统一响应解包与空值保护（避免空包导致崩溃）

**Design**

- 所有关键链路在读取 `res.data.code` 前必须可选链/解包；对 `null/''/'null'/非 JSON` 给出用户可理解提示，并引导“重试/检查网络/去订单详情继续”。

**Tech**

- 优先在调用点做最小修复（避免修改 `src/network/*` 造成全局影响），但对“高频复用链路”可在后续考虑加一个轻量 helper（不引入新依赖）。
- 涉及重点页面（首批 P0）：
  - `src/package-order/pages/order-create/index.tsx`
  - `src/package-order/pages/order-matching/index.tsx`
  - `src/package-order/pages/pending-order/index.tsx`
  - `src/package-order/pages/order-processing/index.tsx`
  - `src/package-order/pages/order-publish-feedback/index.tsx`

**Acceptance**

- 任意接口返回空 body/字符串/非 JSON：页面不崩溃，给出可操作提示。

#### P0-2 支付“恢复入口”统一与状态回流

**Design**

- 支付结果（成功/取消/失败/回调延迟）统一落到“订单详情（高亮去支付）”或“匹配页（已支付）”，避免用户迷路与重复下单。

**Tech**

- 前端：在支付 cancel/fail 分支统一导航到 `package-order/pages/order-detail` 并带 `orderId`，详情页负责判断 `pending_payment` 并提供继续支付/补单入口。
- 后端：补单接口与订单状态同步要可被前端安全调用（仅对该订单拥有者）。

**Acceptance**

- 取消支付后，用户能明确“订单未生效/待支付”，并能继续支付直至状态更新。

#### P0-3 发布验证失败兜底（防止交付卡死）

**Design**

- 验证失败必须允许继续闭环：
  - 方案 A：允许提交但标记“待人工核验”（推荐）
  - 方案 B：提供申诉/人工审核入口（短期可落到工单/客服）

**Tech**

- 前端：`order-publish-feedback` 增加“跳过验证提交（需原因）”或“申请人工核验”分支。
- 后端：`order-processing` / `tikhub` 侧记录验证状态与原因，避免静默失败。

**Acceptance**

- 外部验证服务不可用时，接单者仍可提交反馈，发单者仍可验收（可标记风险提示）。

#### P0-4 驳回返工可循环（revision\_requested 循环不丢上下文）

**Design**

- 驳回 → 修改 → 再提交 → 再验收可循环 N 次；订单状态与处理记录状态联动一致。

**Tech**

- 核对 `server/src/modules/order/*`、`order-processing/*` 的状态映射与回写逻辑；前端按“单一可信状态”渲染下一步动作。

**Acceptance**

- 返工链路完整可用，不出现卡死/阶段倒退/验收按钮不可点。

### Phase 2：P1 关闭（可信度/一致性/高频困惑点）

#### P1-1 状态口径统一（列表/详情/处理/验收）

**Design**

- 对外只展示一套“用户可理解”的阶段：待支付→匹配中→待接单→生成中→待发布→待验收→已完成/已取消。

**Tech**

- 后端提供 `orderViewModel`（或在现有接口中补齐聚合字段）保证前端无需自行推导多源状态。
- 前端减少“根据多个字段猜状态”的分支，集中在一处映射。

#### P1-2 账号绑定回流闭环（去绑定→返回自动刷新）

**Design**

- 发布引导里对“未绑定”的提示必须闭环（为什么要绑定、去哪里绑定、回来自动刷新）。

**Tech**

- `package-avatar/pages/avatar-account-config` 完成后通过明确的回流机制（query + didShow refresh 或 eventChannel）触发 publish-guide 刷新。

#### P1-3 通知体系闭环（关键事件必达 + 回跳定位）

**Design**

- 派单、接单、生成失败、验收驳回、支付结果、超时等必须进入站内通知，并支持点击通知跳到订单详情/处理页定位。

**Tech**

- 后端：`notification.service.ts` 统一发通知入口；关键服务点补发（order/order-dispatch/order-processing/payment）。
- 前端：通知列表点击后按 `payload.type + payload.refId` 跳转定位。

### Phase 3：P2 与长期治理（可持续优化，不阻塞内测放行）

#### P2-1 结算透明（规则、预计时间、明细）

#### P2-2 列表分页/筛选/排序（订单广场/订单列表/通知/收益明细）

#### P2-3 增长闭环（推广分享真实落地、邀请码参数验证）

#### P2-4 观测与对账（支付对账、状态机停留时长、超时任务告警）

## Testing Strategy（可跟踪与可回归）

### 1) Smoke Pack（必通 5 条）

1. 发单创建→支付成功→派单→接单→生成→发布反馈→验收通过→完成结算
2. 支付取消→从订单详情继续支付→支付成功→后续同 1
3. 生成失败（超时/服务错）→重试成功→后续同 1
4. 发布验证失败→走兜底→仍可提交→可验收/可完成
5. 验收驳回→修改再提交→再次验收通过→完成结算

### 2) 回归策略

- 每修复一个 P0/P1：必须跑 Smoke Pack 中至少相关 2 条；合并前跑 `pnpm validate`
- 后端关键链路补充脚本化验证（复用 `server/scripts/*` 与 `TEST_PENDING_ORDER_FLOW.md` 的 curl/sql 步骤）

### 3) 数据准备

- 本地：使用 `server/scripts/generate-test-orders.js`、`generate-test-data.js`（若存在）生成可重复测试数据
- 远程：按 `.trae/rules/project_rules.md` 的数据库与 pm2 运维手册执行（执行阶段再落地）

## Assumptions & Decisions

- 端侧仅覆盖微信小程序（WEAPP），H5 不作为内测放行门槛。
- 以“全量主线闭环”为范围，不包含后台（package-admin）验收与修复。
- 不引入新依赖作为前提；如必须引入（例如测试框架），需要先单独提案并评估成本。
- 修复遵循项目变更治理：单次改动一个问题、最小 diff、避免无关格式化与重构。
