# 财务管理界面：产品需求与落地方案（Plan）

## Summary

本规划针对管理端 [finance/index.tsx](file:///Users/aiden/Projects/morena/src/package-admin/pages/finance/index.tsx) 的“财务管理”界面，补齐其背后的产品口径、数据模型与后端闭环，使其满足项目的运营/财务对账需求：

- 同时覆盖「钱包余额充值」与「订单支付收入」两条资金来源（用户已确认“两者都要”）。
- 以 `withdrawal_requests` 作为提现审核唯一事实源（用户已确认）。
- 分佣采用“混合模式”：既保留固定拉新奖励，也支持按比例订单分佣（用户已确认）。
- 财务流水 `transactions` 全量覆盖：提现/分佣/订单收入/余额充值均落统一流水（用户已确认）。

## Premise / Constraints / Boundaries / Endgame

### Premise
- 该项目存在 C 端收益中心（提现/收益明细）与管理端财务管理（统计/流水/提现审核）两条链路，需要统一口径。
- 当前管理端 UI 已具备统计卡片、类型筛选、交易列表、提现审核（通过/驳回）基础交互，但核心数据闭环存在割裂（详见 Current State）。

### Constraints
- 全局路由前缀已是 `/api`，后端路由装饰器不可再手动写 `api`。
- 变更必须符合“手术式修改”原则：按闭环拆分、避免无关重排/重构；每阶段落地需可验证（`pnpm validate`）。
- 资金相关逻辑需要可追溯：所有余额变化必须落 `transactions`（可对账、可回溯、可审计）。

### Boundaries（允许改动范围）
本方案在执行阶段预计只围绕“财务/钱包/支付/分佣”范围改动，主要文件候选（以实际落地阶段拆分为 1–3 文件/批次）：
- 管理端财务 UI： [finance/index.tsx](file:///Users/aiden/Projects/morena/src/package-admin/pages/finance/index.tsx)
- C 端收益中心： [earning-center/index.tsx](file:///Users/aiden/Projects/morena/src/package-profile/pages/earning-center/index.tsx)
- 后端财务/管理： [admin.controller.ts](file:///Users/aiden/Projects/morena/server/src/modules/admin/admin.controller.ts), [admin.service.ts](file:///Users/aiden/Projects/morena/server/src/modules/admin/admin.service.ts)
- 后端收益/提现： [earnings.controller.ts](file:///Users/aiden/Projects/morena/server/src/modules/earnings/earnings.controller.ts), [earnings.service.ts](file:///Users/aiden/Projects/morena/server/src/modules/earnings/earnings.service.ts)
- 后端支付回调： [wechat-pay.service.ts](file:///Users/aiden/Projects/morena/server/src/modules/payment/wechat-pay.service.ts)
- 后端分佣： [referral.service.ts](file:///Users/aiden/Projects/morena/server/src/modules/referral/referral.service.ts)
- 数据库初始化脚本（用于对齐表结构/字段口径）： [init_database.sql](file:///Users/aiden/Projects/morena/server/init_database.sql)（以及线上迁移 SQL，执行阶段再定）

### Endgame（验收标准）
- 管理端财务页四张卡片与列表数据可真实跑通：
  - 累计充值（钱包充值总额）
  - 累计提现（已审核通过且完成出款的总额，或至少“已审核通过”）
  - 累计分佣（固定拉新奖励 + 按比例订单分佣）
  - 待审核提现（`withdrawal_requests.status=pending` 总额）
  - 交易列表可按 type 筛选，能看到每笔的用户、金额、状态、描述与时间。
- C 端提现申请写入 `withdrawal_requests` 并导致余额冻结；管理端审核通过/驳回可正确影响余额（通过：扣减冻结；驳回：解冻回可用）。
- `transactions` 对所有余额变化有对应记录，可用于对账与问题追溯。

## 产品需求（PRD级别）

### 用户角色
- 超级管理员：查看全局资金盘、处理提现审核、查看流水、对账。
- 财务运营：日常审核提现、排查异常、导出对账（导出可作为后续增强）。

### 核心任务（Jobs-to-be-done）
1. 快速判断资金盘健康度：充值/收入、提现、分佣成本、待处理提现压力。
2. 快速处理待审核提现：通过/驳回，留存原因；确保用户侧余额状态一致。
3. 追踪每笔资金事件：可按类型过滤，定位某用户某笔资金变化的来源（订单/充值/分佣/提现）。
4. 支撑对账与风控：统一流水表，可做审计与追溯；为后续“异常检测/黑名单/限额”留扩展点。

### 口径定义（必须先统一）
- 充值（recharge）：用户通过微信支付“充值到钱包余额”的金额（增加用户可用余额）。
- 订单（order）：用户支付订单的金额（平台收入，不直接进入用户余额；但应进入平台侧统计，并可落入财务流水用于对账）。
- 分佣（commission）：两部分之和：
  - 固定拉新奖励（现有 referral_bonus 等）
  - 按订单金额比例分佣（commission_rate * 订单实付金额），可按邀请关系归因
- 提现（withdraw）：用户把可用余额申请提现（冻结→审核→出款/驳回）。

### 管理端页面交互规则（对应现有 UI）
- 顶部四卡：
  - 累计充值：`SUM(transactions.amount WHERE type='recharge' AND status='completed')`
  - 累计提现：`SUM(transactions.amount WHERE type='withdraw' AND status='completed')`
  - 累计分佣：`SUM(transactions.amount WHERE type='commission' AND status='completed')`
  - 待审核提现：`SUM(withdrawal_requests.amount WHERE status='pending')`（也可从 transactions 计算 pending）
- 类型筛选：
  - all / recharge / withdraw / commission / order
  - 筛选应仅影响列表，不影响顶部四卡（保持全局口径）。
- 提现审核：
  - 仅 `type=withdraw & status=pending` 的列表项出现“通过/驳回”按钮。
  - 驳回必须填写原因（现有弹窗已具备）；后端需保存到 withdrawal_requests（以及对应 transactions/notes）。

## 数据模型与账务规则（核心）

### 核心原则
- “余额变化必落流水”：只要影响 `users.balance / users.frozen_balance`，就必须写入 `transactions`，且具备可回溯 reference。
- “提现审核可重放”：审核动作本身也应有对应流水/状态变更记录，保证后续追责与对账。

### 建议的统一字段/枚举
- `transactions.type`：`recharge | withdraw | commission | order`
- `transactions.status`：
  - `pending`：事件已发生但未最终结算（如提现申请中）
  - `completed`：已结算（充值入账、分佣发放、提现完成、订单已支付）
  - `rejected`：被拒绝/失败（提现驳回、充值失败等）
- `transactions.reference_id`：
  - recharge：`payment_orders.id` 或 `out_trade_no`
  - order：`orders.id` 或 `payment_orders.id`
  - commission：`referrals.id` 或 `orders.id`（按比例分佣时）
  - withdraw：`withdrawal_requests.id`

### 表结构对齐策略（以 withdrawal_requests 为事实源）
由于现状存在 `withdrawals` 表（[init_database.sql](file:///Users/aiden/Projects/morena/server/init_database.sql#L507-L523)）与 `withdrawal_requests`（代码在用），执行阶段采取：
1. 以 `withdrawal_requests` 为主：C 端提现申请改写入 `withdrawal_requests`。
2. 对已有 `withdrawals` 表：
   - 若线上已在用：可保留作为“历史表”，并在管理端查询时做兼容合并（仅过渡期）。
   - 迁移策略：提供一次性迁移 SQL（withdrawals → withdrawal_requests），迁移后冻结写入 withdrawals。

## 分阶段落地（确保每阶段可验收）

### Phase A：统一提现事实源 + 审核闭环（先救火）
- 改造 C 端提现申请写入 `withdrawal_requests`（并冻结余额）
- 管理端审核通过/驳回时同步更新余额与流水状态
- 产出：待审核提现卡片与提现列表可真实驱动审核动作

### Phase B：补齐 transactions 写入规则（形成可对账流水）
- 充值入账、提现申请/审核、分佣发放、订单支付成功均写 `transactions`
- 补齐 `transactions.balance_before/balance_after`（如果采用余额口径；订单收入可留空或写平台侧字段）

### Phase C：充值到余额（recharge）闭环
- 新增充值支付入口（API 或前端入口）
- 支付回调分支支持 `order_type='recharge'`：入账 users.balance + 写流水

### Phase D：分佣混合模式落地
- 固定拉新奖励：保持现状入账，但补齐 transactions(commission)
- 按比例订单分佣：在订单支付成功后，根据邀请关系/配置计算分佣并入账（写 earnings + users.balance + transactions）
- 管理端统计：累计分佣=两者之和，列表可追溯来源（reference_id）

## Verification（执行阶段的验证方式）
- 静态检查：`pnpm validate` 通过（包含 lint+tsc）。
- 手工用例（最小闭环）：
  - 用测试用户发起提现申请 → 管理端看到 pending → 驳回/通过 → C 端余额与冻结余额变化正确 → 管理端列表状态更新正确。
  - 发起充值支付成功 → C 端余额增加 → 管理端“累计充值”增长 → 流水出现 recharge。
  - 支付订单成功 → 管理端“订单”流水出现 → 触发按比例分佣时：邀请人余额增加、分佣流水出现。

## Assumptions & Decisions
- 已确认决策：
  - 充值包含“钱包充值 + 订单支付收入”两条来源，并在财务页分别可查。
  - 提现审核事实源使用 `withdrawal_requests`。
  - 分佣采用“固定+比例”的混合模式。
  - 流水全量覆盖（含充值）。
- 尚需执行阶段进一步确认（不影响本计划结构）：
  - 平台侧“收入/成本/利润”是否需要单独卡片与口径（当前 UI 未展示，可后续增强）。
  - 出款是否需要对接真实打款通道（目前以“审核状态”作为完成节点）。
