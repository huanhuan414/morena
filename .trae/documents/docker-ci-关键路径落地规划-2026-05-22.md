# Docker CI 关键路径落地规划

## Summary

### Premise
- 现状：仓库已具备 `compose.yaml`、`server/Dockerfile`、`.github/workflows/ci.yml`、`pnpm docker:dev`、`pnpm docker:test`，但当前 Docker 主链只覆盖 `db + server-dev` 和 `db + server + api-tests`，还没有把 H5 前端纳入本地联调主路径。
- 目标：以最小可跑通为准，补齐 `前端 H5 + 后端 NestJS + MySQL` 的本地 Docker 联调链路，并让 GitHub Actions 对这条关键路径做持续校验，避免本地可跑、CI 不认，或 CI 通过、本地联调失效。

### Constraints
- 禁止事项：本次不规划生产 CD、不改远端服务器发布方式、不引入新基础设施、不扩展到小程序发布链路。
- 质量红线：保留现有 `pnpm validate`、`pnpm build:ci`、`pnpm docker:test` 作为门禁；新增链路必须可被 README 明确复现。

### Boundaries
- 允许改动文件：
  - `compose.yaml`
  - `server/Dockerfile`
  - `package.json`
  - `config/index.ts`
  - `config/dev.ts`
  - `.dockerignore`
  - `.env.example`
  - `.github/workflows/ci.yml`
  - `README.md`
  - 新增一个前端开发容器 Dockerfile（建议：`Dockerfile.web-dev`）
- 禁止改动内容：
  - 业务页面、接口实现、数据库 schema、远端部署脚本、PM2/生产服务器配置

### Endgame
- 验收标准：
  - 一条命令可拉起本地 `db + server-dev + web-dev`
  - H5 前端容器访问后端走容器内网络，不误连远端生产域名
  - CI 能校验本地开发容器镜像可构建、后端容器冒烟可通过
  - README 给出明确的启动、排障、停止路径

- [README.md](file:///Users/aiden/Projects/morena/README.md) 已记录现有 Docker 开发/测试链路，但没有“前后端一体联调”的命令、环境变量和故障排查说明。

## Proposed Changes

### Phase 1：收敛本地开发网络口径

- 修改 [config/dev.ts](file:///Users/aiden/Projects/morena/config/dev.ts)
  - What：去掉开发态固定远端 `PROJECT_DOMAIN` 的默认值，改为“默认留空，本地优先走相对路径 `/api`，仅在显式传入环境变量时才覆盖”。
  - Why：否则前端即使放进 Docker，也会继续请求线上域名，无法形成真实本地联调。
  - How：保留 `PROJECT_DOMAIN` 注入能力，但默认值改为空字符串或直接依赖 `config/index.ts` 的基础注入。

- 修改 [config/index.ts](file:///Users/aiden/Projects/morena/config/index.ts)
  - What：把 H5 `devServer.proxy['/api'].target` 从写死的 `http://localhost:3000` 改为可配置变量，例如 `H5_API_PROXY_TARGET`。
  - Why：本机开发需要 `http://localhost:3000`，Docker 前端容器需要 `http://server-dev:3000` 或 `http://server:3000`。
  - How：默认仍回落到 `http://localhost:3000`，当 Compose 注入变量时覆盖；保留现有 `host: '0.0.0.0'` 和端口 `5000`。

- 修改 [.env.example](file:///Users/aiden/Projects/morena/.env.example)
  - What：补充 `H5_API_PROXY_TARGET`、`WEB_PORT`（如需要）以及“本地联调建议留空 `PROJECT_DOMAIN`”说明。
  - Why：把网络入口显式化，避免不同开发者各自手改配置。
  - How：给出本机开发默认值示例，并注明 Docker 场景由 Compose 注入覆盖。

### Phase 2：补齐前端 Docker 开发容器

- 新增 `Dockerfile.web-dev`（建议路径：`/Users/aiden/Projects/morena/Dockerfile.web-dev`）
  - What：新建一个面向工作区的开发镜像，安装根依赖，支持执行 `pnpm dev:web`。
  - Why：现有 [server/Dockerfile](file:///Users/aiden/Projects/morena/server/Dockerfile) 只服务后端；强行复用会让前端构建上下文和职责混乱。
  - How：
    - 基于 `node:20-bookworm-slim`
    - 启用 `corepack`
    - 复制根 `package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`patches/`
    - 安装 workspace 依赖
    - 运行时通过 bind mount 挂载前端源码目录
    - 默认命令由 Compose 指定为 `pnpm dev:web`

- 修改 [.dockerignore](file:///Users/aiden/Projects/morena/.dockerignore)
  - What：为前端开发镜像放开最小必需文件白名单。
  - Why：当前上下文只允许 `server/**`，前端镜像无法获取 `src/`、`config/`、`public/` 等必要文件。
  - How：最小化放开以下路径：
    - `src/**`
    - `config/**`
    - `public/**`
    - `babel.config.js`
    - `tsconfig.json`
    - `project.config.json`
    - `project.tt.json`
    - 其他经 Taro H5 开发确认为必需的根级配置

- 修改 [compose.yaml](file:///Users/aiden/Projects/morena/compose.yaml)
  - What：新增 `web-dev` 服务，形成 `db + server-dev + web-dev` 联调链。
  - Why：当前只有后端开发容器，前端仍需宿主机运行，不能满足“前后端一体联调”目标。
  - How：
    - 新增 `web-dev` profile 或将其纳入现有 `dev` profile
    - `build.context` 指向仓库根目录，`dockerfile` 指向新增的 `Dockerfile.web-dev`
    - 暴露 `5000`
    - 注入 `H5_API_PROXY_TARGET=http://server-dev:3000`
    - 注入空 `PROJECT_DOMAIN`，强制走本地代理
    - bind mount 挂载 `src/`、`config/`、`public/`、根配置文件，保持热更新
    - 视需要增加 `depends_on: server-dev`

- 修改 [package.json](file:///Users/aiden/Projects/morena/package.json)
  - What：把 `docker:dev` 从只拉起 `db server-dev` 改为拉起 `db server-dev web-dev`，必要时补一个更清晰的别名如 `docker:dev:fullstack`。
  - Why：用户目标是“一条命令跑通最小本地联调”，命令入口需要直达目标。
  - How：保留现有 `docker:test` 不变，避免影响后端容器冒烟链。

### Phase 3：让 CI 守住这条关键路径

- 修改 [.github/workflows/ci.yml](file:///Users/aiden/Projects/morena/.github/workflows/ci.yml)
  - What：在现有 `quality` + `docker-smoke` 基础上，增加对前端开发容器构建能力的校验。
  - Why：如果只校验宿主机 `pnpm build:web`，本地 Docker 联调所依赖的 `web-dev` 镜像可能长期失效而不被发现。
  - How：
    - `quality` 继续保留 `pnpm validate` 和 `pnpm build:ci`
    - 在 `docker-smoke` 中先执行 `docker compose --profile dev build web-dev server-dev`
    - 再执行现有 `pnpm docker:test`，验证 `db + server + api-tests`
    - 收尾继续 `docker compose down -v`

- 可选但推荐：在 CI 里增加 `docker compose config` 校验
  - What：在执行前输出并校验 Compose 合成结果。
  - Why：能更早发现 profile、环境变量、服务名拼写错误。
  - How：放在 `docker-smoke` 开头，失败即终止。

### Phase 4：补齐文档与故障排查路径

- 修改 [README.md](file:///Users/aiden/Projects/morena/README.md)
  - What：补充“前后端一体 Docker 本地联调”章节与 CI 关键路径说明。
  - Why：当前文档只覆盖后端开发容器与后端冒烟容器，不足以指导新同学复现完整链路。
  - How：

    - 标明最小排障步骤：看 `docker compose logs -f web-dev server-dev db`
    - 标明 `PROJECT_DOMAIN` 在本地开发默认应为空

## Assumptions & Decisions

- 决策：本次只做 `CI` 和本地开发关键路径，不进入生产 `CD`。
- 决策：本地最小闭环以 H5 为主，不把微信/头条小程序构建纳入 Docker 联调。
- 决策：后端继续复用 [server/Dockerfile](file:///Users/aiden/Projects/morena/server/Dockerfile)，前端单独新增开发镜像，避免一个 Dockerfile 混杂两类职责。
- 决策：CI 不追求镜像推送、远端部署、矩阵构建，只验证“能构建、能启动、能冒烟”三件事。
- 假设：本地前端联调只依赖 H5 `devServer`，不需要额外静态 Nginx 容器。
- 假设：`api-tests` 仍只验证后端基础健康和最小 API 冒烟，不扩展高价值业务流测试。

## Verification Steps

- 本地验证
  - `pnpm docker:down`
  - `pnpm docker:dev`
  - 打开 `http://localhost:5000`，确认 H5 可访问
  - 在 H5 中访问任一走 `Network.request('/api/...')` 的页面，确认请求命中本地后端而非远端域名
  - `docker compose logs --tail=100 web-dev server-dev db`

- 容器测试验证
  - `pnpm docker:test`
  - 确认 `api-tests` 至少通过 `GET /api/hello`、`GET /api/health`

- CI 验证
  - `pnpm validate`
  - `pnpm build:ci`
  - `docker compose --profile dev build web-dev server-dev`
  - `docker compose --profile test up --build --abort-on-container-exit --exit-code-from api-tests api-tests`
