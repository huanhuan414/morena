# Task1 附录：概念词典、状态口径、用户旅程断点与能力缺口

## 1. 核心概念词典（统一口径）
- **用户（User）**：使用 Morena 的自然人账号；可同时具备“供给侧/需求侧”身份。
- **供给侧（Supply）**：通过分身接单并交付内容的一侧（个人/工作室/代理商）。
- **需求侧（Demand）**：创建订单、验收交付并支付的一侧（品牌方/商家/跨境团队/运营方）。
- **分身（Avatar）**：可被平台化托管、可被指派订单并产出内容的“交付资产”；包含人设、能力、平台绑定信息、产出偏好与可用性。
- **托管（Managed / 托管模式）**：允许系统在规则约束内，替用户自动完成“接单→生成→发布/回传→验真→结算”链路中的部分动作；托管并不等于完全自动化，关键节点可要求用户确认。
- **平台账号绑定（Platform Binding）**：将分身与特定内容平台的账号关联，用于发布与证据回传；不同平台发布形态与风控规则不同。
- **订单（Order）**：需求侧发起的可计价任务包；订单不等于“分发”或“履约”，它是驱动全链路的业务载体。
- **分发（Dispatch）**：将订单在规则与供需约束下指派给具体分身/供给侧的过程；分发结果可以被接受、拒绝或超时。
- **接单（Accept）**：供给侧对分发结果的确认动作；接单后进入履约，并产生 SLA 与超时规则。
- **履约（Fulfillment）**：订单从“接单”到“完成交付”的执行阶段，包含内容生成、修改、发布/回传等步骤。
- **内容生成（Generation）**：使用 AI 或混合方式生成交付物（文案/脚本/图片/视频/标题等）；生成结果通常需要“预览→修改→确认”闭环。
- **发布（Publish）**：将交付内容发布到目标平台；发布可由系统辅助完成，也可由用户手动发布后回传凭证。
- **回传（Proof Submission）**：供给侧提交可用于验真的证据（链接/截图/作品 ID 等）。
- **验真（Verification）**：平台化规则对回传证据进行校验，确认交付是否真实可追溯；验真失败应给出可解释原因与修正路径。
- **结算（Settlement）**：在验真通过后，对订单金额进行平台/供给侧分账并入账的过程。
- **收益（Earnings）**：供给侧可提现的累计金额（已结算、可提现、冻结、提现中等拆分口径）。
- **提现（Withdrawal）**：供给侧将可提现余额提取到外部账户的过程。
- **邀请（Referral）**：用户邀请新用户并形成交易后的返利机制；返利应以“已验真并完成结算”的订单为准。

## 2. 状态口径（订单/分发/履约/验真/结算）
### 2.1 基本原则
- **拆分 5 类状态机**：订单、分发、履约、验真、结算各自独立演进，避免“一个状态字段试图表达所有阶段”导致口径混乱。
- **单一状态源**：每类状态机必须有唯一维护者（模块/服务）与唯一对外口径；页面展示仅做衍生聚合，不反向写回。
- **失败原因可枚举**：凡是影响用户信任与转化的失败/驳回，必须有枚举原因（可统计、可解释、可修复）。

### 2.2 订单状态（OrderStatus）
| 状态 | 含义 | 进入条件 | 退出条件 | 主要展示对象 |
| --- | --- | --- | --- | --- |
| draft | 草稿未提交 | 需求侧创建但未提交 | 提交订单 | 需求侧 |
| submitted | 已提交待处理 | 提交成功 | 进入可分发/被拒绝 | 需求侧、运营 |
| dispatching | 分发中 | 可分发且开始匹配 | 分发成功/失败/取消 | 供需两侧、运营 |
| in_fulfillment | 履约中 | 分发被接单 | 履约完成/失败/取消 | 供需两侧 |
| verifying | 验真中 | 已回传证据 | 验真通过/驳回/超时 | 供需两侧 |
| completed | 完成（可结算或已结算） | 验真通过 | 结算完成（可作为子状态） | 供需两侧 |
| cancelled | 已取消 | 需求侧/运营取消 | 无 | 供需两侧 |
| rejected | 订单不予受理 | 风控/规则拒绝 | 无 | 需求侧、运营 |

### 2.3 分发状态（DispatchStatus）
| 状态 | 含义 | 关键规则（建议口径） |
| --- | --- | --- |
| pending | 待分发 | 订单进入 dispatching 后生成分发任务 |
| dispatched | 已指派待响应 | 已推送给目标分身/供给侧 |
| accepted | 已接单 | 进入履约，产生 SLA 与超时 |
| rejected | 已拒单 | 进入重分发或回到分发池 |
| expired | 超时未响应 | 到期未接单，进入重分发或失败 |
| failed | 分发失败 | 无可用分身/风控拦截/系统异常 |

### 2.4 履约状态（FulfillmentStatus）
| 状态 | 含义 | 关键规则（建议口径） |
| --- | --- | --- |
| not_started | 未开始 | 接单后尚未进入生成 |
| generating | 生成中 | 生成任务运行/排队中 |
| preview_ready | 预览可用 | 生成结果已产出，等待确认/修改 |
| revising | 修改中 | 有修改请求在处理中（可计数） |
| ready_to_publish | 待发布 | 内容确认完成，等待发布/回传 |
| published | 已发布/已回传 | 已发布且有可验真的凭证 |
| failed | 履约失败 | 生成失败/超时/违规/用户放弃 |
| cancelled | 履约取消 | 订单取消导致履约终止 |

### 2.5 验真状态（VerificationStatus）
| 状态 | 含义 | 关键规则（建议口径） |
| --- | --- | --- |
| not_submitted | 未提交凭证 | 尚无回传信息 |
| submitted | 已提交待验真 | 回传成功进入队列 |
| approved | 通过 | 进入结算资格 |
| rejected | 驳回 | 必须给出可枚举原因与修正动作 |
| expired | 超时未补证 | 驳回后超过补证时限 |

### 2.6 结算状态（SettlementStatus）
| 状态 | 含义 | 关键规则（建议口径） |
| --- | --- | --- |
| not_eligible | 不可结算 | 未验真通过或订单取消 |
| eligible | 可结算 | 验真通过，待入账 |
| settled | 已结算 | 分账入账成功，计入收益 |
| payout_failed | 结算失败 | 资金通道/风控失败，需可追踪原因 |

## 3. 两条用户旅程与关键断点（P0/P1）
### 3.1 旅程 1：供给侧（分身托管接单）
#### 主路径
登录/注册 → 创建分身 →（可选）绑定平台账号 → 开启托管 → 等待分发 → 接单 → 履约（生成/修改/发布/回传）→ 验真 → 结算 → 收益提现 → 邀请/复购

#### P0 断点（主链阻塞，Phase 0 必须优先修复/统一口径）
- **托管含义不清/开关无后果**：用户无法理解开启后系统会做什么、哪些节点需要确认，导致不敢开启或开启后预期落差。
- **分发/接单触达失败**：未能及时通知到供给侧或入口不明显，造成超时与分发失败。
- **状态不一致/同义不同名**：订单详情、列表、后台看到的状态口径不同，用户无法判断“我现在该做什么”。
- **回传失败或证据要求不明确**：需要链接/截图/作品 ID 但缺少模板与示例，回传失败后无法定位原因。
- **验真驳回不可解释**：驳回原因不清或不可修正，直接损害信任并导致流失。
- **结算/收益口径不透明**：通过验真后收益未入账或展示滞后，用户认为平台不可信。

#### P1 断点（体验与转化提升，Phase 1 重点优化）
- **分身创建信息负担过重**：缺少默认人设/模板/引导，创建成本高。
- **履约修改闭环低效**：修改次数/时限不明确，导致反复沟通或拖延。
- **平台差异适配不足**：不同平台的发布形态、素材规格、风控提示缺少差异化规则。
- **提现流程与风控解释不足**：失败/冻结原因不透明，缺少自助修复路径。

### 3.2 旅程 2：需求侧（发单交付验收）
#### 主路径
登录/注册 → 创建订单（平台/目标/预算/要求）→ 支付/发布 → 等待分发/接单 → 查看进度 → 预览交付物 → 要求修改/确认发布 → 验真 → 验收/争议 → 完成/结算

#### P0 断点（主链阻塞，Phase 0 必须优先修复/统一口径）
- **订单创建字段口径不清**：平台/目标/交付物/验真要求不明确，导致订单质量不稳定，后续履约失败。
- **支付/提交后无确定性反馈**：订单进入“分发/履约/验真”的状态不透明，需求侧无法判断是否需要等待或补充信息。
- **进度不可追踪**：缺少关键节点（接单、预览、发布、回传、验真）的可解释进度，易引发投诉与争议。
- **争议/取消口径缺失**：需求侧无法合理取消或发起争议，平台无法运营化处理。

#### P1 断点（体验与转化提升，Phase 1 重点优化）
- **订单模板化不足**：缺少行业/平台任务模板，导致新手难以写清需求。
- **SLA 与修改规则不明确**：修改次数、超时、补证据时限缺少产品化约束，导致纠纷成本高。
- **质量预期管理不足**：缺少“示例/能力边界/风险提示”，造成交付预期落差。

## 4. 现有能力覆盖 vs 规划缺口（对齐代码现实）
| 领域 | 现有能力覆盖（从代码与页面结构抽象） | 规划缺口（建议标注优先级） |
| --- | --- | --- |
| 分身（Avatar） | 创建/管理、托管开关、基础资料与能力配置 | P0：分身“可接单/不可接单”判定口径与原因；P1：模板化创建与分层引导 |
| 平台绑定/发布 | 存在平台账号与发布入口、回传凭证入口 | P0：不同平台发布/回传字段统一与差异化规则；P1：一键发布与失败自助修复 |
| 订单（Order） | 订单广场/列表/详情、基础创建与查看 | P0：订单创建字段口径与质量准入；P1：行业/平台模板与预算建议 |
| 分发（Dispatch） | 具备分发与接单链路 | P0：分发状态枚举与超时/重分发规则一致；P1：质量排序与策略可配置 |
| 履约（Fulfillment） | 生成任务、轮询/查询、基础执行状态 | P0：履约状态口径与失败原因枚举；P1：修改闭环（次数/时限/追踪）产品化 |
| 验真（Verification） | 链接校验/截图/凭证回传验真存在 | P0：驳回原因可解释、可修复；P1：申诉/补证据闭环与原因统计看板 |
| 结算/收益 | 收益概览/提现、结算相关链路存在 | P0：收益口径（可提现/冻结/处理中）与结算时点一致；P1：提现失败的自助修复与风控解释 |
| 增长（Referral/活动/通知） | 邀请返利、活动曝光/点击、通知中心 | P0：返利以“已验真并结算”为准的统一口径；P1：分层激励与召回策略 |
| 后台（Admin） | 用户/分身/订单/财务/内容/邀请/活动等入口 | P0：主链漏斗与失败分布最小看板；P1：策略配置（分发/风控/验真规则）可视化 |
