# Task4 附录：Phase 0/1/2/3 能力清单、依赖、验收门槛、回滚策略与风险清单

## 0. 使用说明（约束与口径）
- 本附录在 [task1-appendix.md](./task1-appendix.md) 的“概念词典/状态口径”与 [task2-appendix.md](./task2-appendix.md) 的“KPI Tree/漏斗”之上落地，所有 Phase 的验收均必须可映射到 KPI Tree 指标或主链状态机一致性。
- 所有 Phase 的目标都服务于同一条主链：分身托管接单 → 分发/接单 → 履约（生成/修改/发布/回传）→ 验真 → 结算/收益 → 提现/复购/邀请。
- 验收门槛按“可上线（Gate）/可规模化（Scale Gate）”分层：每期至少满足可上线门槛；若未达到可规模化门槛，允许上线但必须执行“保守开关策略”（限制流量/限制入口/白名单）。
- 回滚策略默认优先顺序：降级策略（Feature Flag/白名单/限流）→ 回退业务策略（分发/验真/结算规则）→ 回退页面入口（隐藏功能）→ 回滚代码版本（最后手段）。

## 1. Phase 总览（能力与依赖关系图）
### 1.1 Phase 目标一句话
- Phase 0：口径收敛与可衡量（能跑通且能算账）
- Phase 1：提升履约成功率（把成功率打上去）
- Phase 2：扩大供需与商业化（把规模做上来）
- Phase 3：平台化与组织化交付（从产品到系统）

### 1.2 关键依赖（跨 Phase）
- 单一状态源：订单/分发/履约/验真/结算 5 类状态机在前后端、后台口径一致（Phase 0 Gate）。
- 可观测性：KPI Tree 与失败原因可统计、可下钻（Phase 0 Gate），否则后续 Phase 的“优化”无法证明有效。
- 可回滚：核心策略（分发、验真、结算、商业化）必须可开关/可灰度/可回退到基线逻辑（Phase 0/1 必须补齐）。

## 2. Phase 0：口径收敛与可衡量（能跑通且能算账）
### 2.1 能力清单（按领域）
#### 2.1.1 产品口径与状态机
- 核心概念与 5 类状态机字段在前台（供给/需求）与后台展示一致，并可由“唯一维护者”写入。
- 失败原因枚举可落库、可统计：分发失败/超时、履约失败、验真驳回、结算失败/冻结等必须有原因码。
- 主链动作与状态映射表：用户在“某状态”下能做什么（下一步动作）一致且可解释。

#### 2.1.2 数据闭环与看板
- 北极星指标 Verified GMV 的计算口径固定：仅统计“验真通过且结算完成”的订单金额（或毛利），并可按平台/渠道/订单类型/供需用户分层。
- 最小漏斗可跑通：获客→激活→分发→履约→验真→结算；每一步至少有成功/失败/超时三个分支计数。
- 失败原因下钻：至少覆盖分发失败、验真驳回、结算失败的 Top 原因分布。

#### 2.1.3 主链 P0 断点修复（以“阻塞交易闭环”为准）
- 托管含义与风险告知：开启托管前明确系统会自动做什么、哪些节点需要确认、失败/超时如何处理。
- 回传凭证规范化：不同平台至少提供“必填字段模板 + 示例 + 常见失败提示”。
- 验真驳回可修复：驳回原因可解释（原因码+文案）且可走“补证据/重新提交”的明确路径。
- 收益口径一致：已结算/可提现/冻结/提现中 的定义与展示一致，避免“已通过验真但不到账”的信任损伤。

#### 2.1.4 稳定性与应急兜底（最小可用）
- 核心链路（分发、生成、回传、验真、结算）出现系统异常时，有可观测告警与人工兜底路径（运营可介入）。
- 关键任务的重试与幂等口径明确：同一订单的重复回传/重复验真不会造成状态乱跳。

### 2.2 关键依赖（前置条件/不可并行）
- 依赖 Task1：状态机定义、失败原因枚举的最终口径（否则数据无法聚合）。
- 依赖 Task2：指标与漏斗的事件/字段定义（否则 Phase 0 无法验收“可衡量”）。
- 不可并行项：在状态机口径未冻结前，不做分发策略优化与商业化 A/B（避免“指标变化不可解释”）。

### 2.3 验收门槛（Gate）
#### 2.3.1 可上线门槛（Phase 0 Gate）
- 状态一致性：前台（订单列表/详情/进度）、后台（订单管理）对同一订单展示的状态机字段含义一致，无同义不同名。
- 漏斗可跑通：至少能从后台/埋点产出“分发成功率、平均接单时间、验真通过率、结算完成率”四个核心指标。
- 驳回可修复：验真驳回后，用户能在明确路径内完成补证并重新进入 submitted/approved 流程。

#### 2.3.2 可规模化门槛（Phase 0 Scale Gate）
- 失败原因可用：分发失败、验真驳回、结算失败的原因码覆盖率达到“绝大多数订单”（以实际日志/后台核对为准）。
- 数据可下钻：从指标看板能下钻到订单明细并定位失败原因（运营可自助定位，无需研发介入）。

### 2.4 回滚策略（Phase 0）
- 触发条件：状态口径/收益口径出现大面积投诉；漏斗关键指标无法产出；验真/结算链路出现不可控错误。
- 回滚动作：
  - 降级：关闭新引入的状态聚合展示（回退到旧展示），但保留落库字段用于排查。
  - 降级：将验真驳回后的补证入口改为“人工工单/运营介入”兜底。
  - 回退：收益展示仅显示“已结算/提现中”两段式，冻结/失败暂不对外展示但后台保留。
  - 最后手段：回滚到上一个稳定版本，并冻结新增状态字段的写入（仅读）。

## 3. Phase 1：提升履约成功率（把成功率打上去）
### 3.1 能力清单（按领域）
#### 3.1.1 分发策略与 SLA
- 分发排序：引入“分身质量/可用性”的排序维度（历史通过率、超时率、拒单率、平台匹配度）。
- 超时/拒单/重分发规则产品化：超时阈值、重分发次数上限、失败兜底（回到广场/运营介入）明确。
- 通知触达增强：分发到达、接单倒计时、驳回补证提醒等必须可靠触达（含多渠道兜底）。

#### 3.1.2 履约闭环（生成→预览→修改→发布/回传）
- 预览与修改规则：修改次数上限、每次修改的时限、修改原因分类（需求变更/生成质量/平台合规）可统计。
- 发布/回传体验：一键发布/回传（或“发布向导”）优先减少用户出错概率；回传前置校验（链接格式/平台字段）更严格。

#### 3.1.3 验真体验与争议最小闭环
- 驳回原因可解释且可统计：驳回原因 TopN 可在后台直接看到，并可关联到平台/订单类型/供给侧分层。
- 争议/取消的口径最小化：至少明确“可取消窗口、取消后资金/结算如何处理、运营介入入口”。

### 3.2 关键依赖（前置条件/不可并行）
- 依赖 Phase 0 Scale Gate：否则无法判断策略优化是否有效。
- 不可并行项：在分发策略可回滚/可灰度前，不允许全量替换算法或大幅改动接单入口。

### 3.3 验收门槛（Gate）
#### 3.3.1 可上线门槛（Phase 1 Gate）
- 分发可控：分发策略可灰度、可按平台/城市/供给分层生效，可一键回退到基线策略。
- 修改闭环有规则：修改次数与时限对供需两侧可见，且能落到订单/履约明细中。
- 验真成功率可提升验证：至少能在看板上看到“验真通过率、驳回原因分布”的变化趋势。

#### 3.3.2 可规模化门槛（Phase 1 Scale Gate）
- 分发效率提升：平均接单时间、超时率、拒单率出现可解释的持续改善（以对照组或上线前后趋势为准）。
- 履约稳定：生成失败率、发布/回传失败率可控，且失败原因可聚合为 TopN 可运营项。

### 3.4 回滚策略（Phase 1）
- 触发条件：分发成功率/超时率显著恶化；用户投诉“接不到单/被误分发/规则不清”；验真驳回激增。
- 回滚动作：
  - 降级：关闭新的排序与策略，回退到“先到先得/基础匹配”的基线分发。
  - 降级：将自动重分发改为运营手动分发（白名单订单）。
  - 回退：修改次数/时限规则从强约束改为弱提示（避免大量存量订单违约）。
  - 回退：一键发布失败时退回“发布向导 + 手动回传”。

## 4. Phase 2：扩大供需与商业化（把规模做上来）
### 4.1 能力清单（按领域）
#### 4.1.1 订单供给扩张与质量治理
- 订单模板化：按平台/行业提供任务模板、交付物示例与预算建议，降低需求侧表达成本。
- 订单准入与风控：预算下限、平台合规字段校验、黑名单词/违规类目拦截。
- 需求侧进度透明：对需求侧展示可解释进度与 SLA（接单/预览/发布/验真/结算）。

#### 4.1.2 供给扩张与激励
- 分身创建模板化与分层：不同供给侧（新手/成熟/工作室）有不同引导与默认配置。
- 托管激励与等级：以“验真通过订单数/通过率/超时率”作为升级条件，权限/曝光与等级挂钩。

#### 4.1.3 商业化与结算体验
- 订阅/抽成组合的可配置与 A/B：不同用户分层可见不同定价/权益组合，且可按渠道灰度。
- 提现与资金通道稳定：提现失败/冻结原因可解释，并有自助修复路径或运营介入流程。
- 邀请返利与活动归因：返利严格绑定“已验真且已结算”的订单，避免作弊与口径争议。

### 4.2 关键依赖（前置条件/不可并行）
- 依赖 Phase 1 Scale Gate：否则扩大供需会放大失败与投诉。
- 不可并行项：在结算/提现失败原因不可解释之前，不应强推商业化提价（否则形成信任危机）。

### 4.3 验收门槛（Gate）
#### 4.3.1 可上线门槛（Phase 2 Gate）
- 模板可用：订单模板在主入口可见且能显著降低创建耗时（以埋点/反馈为准）。
- 商业化可控：订阅/抽成策略具备灰度与回退能力；对存量用户不强制切换。
- 资金口径透明：提现失败/冻结有明确原因与处理时限说明（面向用户与运营后台一致）。

#### 4.3.2 可规模化门槛（Phase 2 Scale Gate）
- Verified GMV 可持续增长：增长能归因到“订单数提升/验真通过率提升/客单价提升”的至少一项，并可解释。
- 供需不失衡：分发失败（无可用分身）占比可控，且有明确的供给补齐策略（拉新/激励/运营调度）。

### 4.4 回滚策略（Phase 2）
- 触发条件：商业化转化下滑且投诉上升；供需失衡导致分发失败激增；提现问题导致舆情。
- 回滚动作：
  - 降级：关闭新定价/新权益组合，回退到上一期定价与权益。
  - 降级：订单模板降级为“推荐填写示例”，不强制模板字段（避免拦截过多订单）。
  - 回退：暂停等级/激励的强约束，保留展示但不影响分发排序（避免刷单/作弊）。
  - 应急：对提现链路启用更严格的风控与人工审核，牺牲速度保障资金安全。

## 5. Phase 3：平台化与组织化交付（从产品到系统）
### 5.1 能力清单（按领域）
#### 5.1.1 B2B2C 与团队交付
- 工作室/代理商多分身管理：成员/角色权限、多分身批量配置、订单分配与绩效口径。
- 团队级结算：对公/分账、多账号提现策略、账期与对账工具。

#### 5.1.2 合规与风控体系
- 平台合规规则引擎化：不同平台的发布/回传/验真规则可配置、可迭代。
- 黑白名单与申诉：违规识别、证据链存档、申诉流程与仲裁口径明确。

#### 5.1.3 运营自动化与增长实验
- 活动编排与召回：按生命周期分层触达（新手激活、流失召回、优质供给提升）。
- 增长实验平台化：A/B 实验管理、分层策略实验、反作弊检测与审计。

### 5.2 关键依赖（前置条件/不可并行）
- 依赖 Phase 2 Scale Gate：否则平台化只会扩大管理成本。
- 不可并行项：在合规与证据链未完善前，不应大规模拓展新平台（风险外溢）。

### 5.3 验收门槛（Gate）
#### 5.3.1 可上线门槛（Phase 3 Gate）
- 团队可用：工作室至少能完成“成员管理→分身分配→订单协同→团队级对账”的闭环。
- 合规可追溯：关键违规/驳回有证据链存档与操作审计，运营可复盘。

#### 5.3.2 可规模化门槛（Phase 3 Scale Gate）
- 运营自动化可替代人力：核心策略（触达、分发、验真规则、商业化）至少有一部分能由运营配置迭代。
- 风控可控：作弊/违规/资金风险可被监控与快速止血，且不会频繁依赖研发救火。

### 5.4 回滚策略（Phase 3）
- 触发条件：新平台合规风险爆发；团队结算出现对账混乱；运营自动化误伤导致大量投诉。
- 回滚动作：
  - 降级：将规则引擎改为“配置只读/仅运营建议”，核心判定回退为固定规则。
  - 降级：团队协作功能改为“只读看板 + 人工分配”，暂停自动化分配与结算。
  - 回退：暂停新平台接入与新活动编排，保留核心主链稳定。

## 6. 风险清单（分组、信号、缓解与兜底）
### 6.1 平台合规与内容风控
- 风险：平台规则变化、违规内容触发封号/限流，导致验真失败与供给侧损失。
  - 预警信号：验真驳回率在某平台快速上升；同类驳回原因集中爆发；用户反馈“发布受限/账号异常”。
  - 缓解：平台差异化规则配置；发布前校验与风险提示；高风险类目白名单；证据链留存支持申诉。
  - 兜底/回滚：暂停该平台新订单；验真改为人工复核；对存量订单允许延长补证时限。

### 6.2 供需失衡（供给不足或订单质量不足）
- 风险：分身供给不足导致分发失败；订单质量不足导致履约失败与供给流失。
  - 预警信号：分发失败（无可用分身）占比上升；拒单率/超时率上升；新供给 7 日留存下降。
  - 缓解：供给分层激励与等级；订单准入与模板化；运营调度与定向匹配；对低质量订单限制曝光。
  - 兜底/回滚：对需求侧开启“延迟交付/退款”策略；对供给侧开启补贴/保护期；暂时收紧接单入口。

### 6.3 状态口径与数据口径混乱
- 风险：同一订单在不同页面状态不一致，或指标口径漂移，导致信任损伤与“无法优化”。
  - 预警信号：客服/运营频繁介入解释状态；同一订单的后台与前台展示冲突；看板指标与订单明细对不上。
  - 缓解：单一状态源；状态机变更必须带迁移方案；失败原因枚举版本化；看板下钻到订单明细作为校验。
  - 兜底/回滚：暂时隐藏聚合状态，回退为“关键节点时间线”；冻结新增字段写入，仅保留读取。

### 6.4 资金与结算风险（提现失败、冻结争议、账期不稳）
- 风险：提现失败/冻结不可解释，引发信任危机；结算错误导致资金损失与合规问题。
  - 预警信号：提现失败率上升；冻结金额堆积；用户投诉“验真通过不到账”；对账差异增加。
  - 缓解：提现失败原因与处理时限透明；风控分层（小额自动、大额人工）；对账与审计；结算幂等与重试口径。
  - 兜底/回滚：暂停大额提现；启用人工审核与延迟到账说明；回退到保守的结算策略（牺牲速度保安全）。

### 6.5 策略迭代误伤（分发/验真/商业化策略）
- 风险：策略上线导致指标短期改善但长期伤害供需生态，或误伤优质用户。
  - 预警信号：投诉集中在某分层；关键指标分化（GMV 上升但留存下降）；驳回原因出现“误判”聚集。
  - 缓解：灰度发布 + 对照组；策略可回退；关键人群白名单保护；策略审计日志。
  - 兜底/回滚：立即回退到基线策略；仅保留观测；运营介入处理存量误伤订单。

### 6.6 技术稳定性（生成/队列/通知/三方依赖）
- 风险：生成任务/队列堆积、通知不达、三方接口波动导致履约大面积延迟或失败。
  - 预警信号：生成平均耗时上升；队列长度异常；通知到达率下降；同一错误码激增。
  - 缓解：任务优先级；超时与重试；降级为“手动履约”；关键链路告警与可视化追踪。
  - 兜底/回滚：暂停新订单/新分发；切换到人工处理；关闭非关键功能减少负载。
