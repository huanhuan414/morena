# 分身产品逻辑任务交付方案

## 1. 目标

基于 `tasks.md` 已梳理出的任务 1-11，将工作从“产品梳理”转为“项目执行”，形成一套可交给项目经理推进、由架构师冻结规则、由开发逐步落地的执行方案。

本方案强调两点：

1. 严格遵守依赖顺序，先冻结规则，再分发开发。
2. 使用子代理进行并行摸底，但所有跨模块决策必须串行确认并统一回写。

---

## 2. 角色分工

### 产品经理

- 负责输出单一业务主链：
  `分身发现/创建 -> 托管配置 -> 派单 -> 接单 -> 内容生成 -> 发布 -> 反馈 -> 验收 -> 完结`
- 负责冻结以下业务规则：
  - 分身生命周期
  - 托管语义
  - 订单状态机
  - 发布平台 canonical 口径
  - 验收完成标准
- 负责定义每个任务的验收标准，不直接定义技术实现细节。

### 项目经理

- 负责把任务 5-11 转为可执行 Sprint。
- 负责控制先后顺序，不允许开发跳过架构冻结直接并行修改。
- 负责每日同步、风险升级、跨角色阻塞清除。
- 负责维护“任务状态 + 风险 + 依赖 + 决策记录”。

### 架构师

- 负责冻结单一状态源、接口契约、字段字典、跨模块边界。
- 负责确认下列高风险统一口径：
  - `avatarId / id`
  - `trust_enabled / is_hosted / isHosted`
  - `order / dispatch / processing / publish` 状态流转
  - 平台别名到 canonical key 的映射
- 负责给开发输出“禁止跨越的边界”和“兼容层策略”。

### 开发人员

- 前端开发负责页面参数、页面回流、状态展示、交互闭环和跨端兼容。
- 后端开发负责接口契约、字段兼容、状态推进、数据库读写和聚合逻辑。
- 开发只在架构规则冻结后实现，不自定义业务口径。

### 测试/联调

- 按主链路做回归，不只测单接口。
- 必测路由、缺参、回流、状态同步、发布反馈、验收完成。

## 4. 调用顺序

所有工作必须按以下顺序推进：

### 第一步：产品经理确认业务规则

先完成：

- 主链确认
- 页面入口确认
- 验收标准确认

输出给项目经理的内容必须是“冻结版”，不能仍然带多个可选方向。

### 第二步：项目经理组织架构冻结会

只讨论以下内容：

- 状态机
- 参数口径
- 字段字典
- DTO 结构
- 平台 canonical 规则

会议产出必须形成书面结论，作为开发唯一依据。

### 第三步：架构师拆技术任务

拆分为：

- 前端任务
- 后端任务
- 联调任务
- 回归任务

拆分后再交给开发，不允许产品经理直接对接多名开发分别提需求。

### 第四步：开发按执行包串行推进

建议顺序：

1. 执行包 A
2. 执行包 B
3. 执行包 C
4. 执行包 D

其中：

- B 未完成，不允许 C 全面联调
- C 未完成，不允许 D 验收闭环

### 第五步：联调与回归

项目经理组织前后端和测试做主链回归：

1. 分身创建与查看
2. 分身托管与好友入口
3. 发单与派单
4. 接单与内容生成
5. 发布引导与反馈
6. 验收与订单完成

---

## 5. 同步机制

### 每日同步

项目经理每天维护 4 项：

- 昨日完成
- 今日计划
- 阻塞项
- 是否影响后续执行包

### 决策同步

涉及以下问题时，必须升级为架构决策，不允许开发自行定：

- 新增状态
- 变更状态含义
- 变更字段主口径
- 变更平台 canonical 映射
- 变更页面跳转参数协议

### 代码同步

同步规则：

- 架构规则文档先更新，再改代码
- 后端接口契约先稳定，再改前端消费
- 前后端联调前必须给出样例响应
- 联调完成后再回写 `tasks.md` 或执行文档状态

### 风险同步

以下风险必须每日跟踪：

- 参数双轨
- 字段双轨
- 状态双轨
- 平台别名不一致
- 回流逻辑断裂
- 页面和接口 contract 漂移

## 6. 子代理使用策略

子代理只用于“摸底、拆解、专项分析”，不用于绕过主流程做最终决策。

### 推荐调用顺序

1. `search`
   - 用于先摸清代码上下文、关键文件、现状断点
2. `backend-architect`
   - 用于拆后端状态机、接口边界、表结构和同步点
3. `frontend-architect`
   - 用于拆页面参数、交互闭环、平台常量和跨端约束
4. 必要时再使用 `comprehensive-code-analyzer`
   - 用于上线前做质量审计，不放在最前面

### 子代理输出必须回收

项目经理必须把子代理输出整理为：

- 最终任务清单
- 责任人
- 依赖关系
- 冻结结论

不能把不同子代理的建议原样并列下发，否则会造成多口径执行。

验收：

- 订单从接单到完成的状态链在前后端一致

## 8. 项目经理落地模板

项目经理实际下发时，可直接按下面模板执行：

### 给架构师

- 先冻结以下内容：
  - 分身参数协议
  - 托管字段协议
  - 订单状态机
  - 发布状态机
  - 平台 canonical 映射
- 输出：
  - 字段字典
  - DTO 契约
  - 状态迁移表
  - 禁止事项

### 给前端开发

- 先改页面参数和页面回流，再改状态展示。
- 只消费统一 DTO，不自己兼容多套字段，除非架构师明确要求兼容层。
- 每个页面提交时附：
  - 入参说明
  - 接口响应样例
  - 主链自测截图

### 给后端开发

- 先收敛字段和状态，再做功能补丁。
- 统一 controller/service 返回结构。
- 每个接口提交时附：
  - 请求样例
  - 响应样例
  - 状态推进说明

### 给测试/联调

- 按主链回归，不按页面孤立测试。
- 每一轮回归都要覆盖：
  - 路由参数
  - 缺参容错
  - 托管状态
  - 订单状态
  - 发布反馈
  - 验收完成

---

## 9. 结论

这份任务单的正确推进方式不是“把任务平均分给多人并行改”，而是：

1. 产品经理先冻结业务主链和验收标准
2. 项目经理组织架构师冻结技术边界
3. 架构师拆成前后端可执行包
4. 开发按执行包顺序逐步完成
5. 每一阶段都通过同步机制控制多口径风险

只有这样，`分身 -> 订单 -> 发布 -> 验收` 这条链路才不会再次出现参数、字段、状态三套口径并存的问题。
